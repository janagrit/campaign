# Test Strategy

## Objective

Protect the relationship between campaign lifecycle, accepted impression events, billable delivery, the financial ledger, and advertiser-facing reporting.

This is a portfolio simulation, not a test of any named vendor's production platform.

## Risk model

| Risk | Business consequence | Priority | Automated coverage |
|---|---|---:|---|
| Impression admitted after confirmed stop | Delivery against advertiser intent | P0 | Stop boundary |
| Duplicate event charged twice | Incorrect advertiser billing | P0 | Idempotency / retry |
| Spend exceeds campaign budget | Financial exposure | P0 | Budget / concurrency |
| In-flight event dropped or double counted | Delivery and billing disagreement | P1 | Two-phase stop |
| Report differs from ledger | Loss of advertiser trust | P1 | Reconciliation |
| Invalid campaign configuration | Incorrect campaign setup | P1 | Validation |
| Invalid lifecycle transition | Unpredictable campaign state | P2 | Lifecycle |

## Test layers

- API integration: request/response contract, state transitions, ledger and reporting.
- Concurrency: simultaneous event processing and duplicate retries.
- Boundary: accepted-before-stop versus accepted-after-stop.
- Negative: malformed input, unknown resources, invalid state transitions.
- Mutation demonstrations: intentionally injected defects should cause focused test failures.

## Critical invariants

1. One `(campaignId, eventId)` maps to at most one financial ledger entry.
2. No newly accepted impression is admitted after stop confirmation.
3. An event accepted before stop confirmation may finish as in-flight work.
4. Billed spend never exceeds the configured budget.
5. Delivered impression count equals billable ledger entry count in this simplified model.
6. Reported spend equals the sum of ledger entries.

## Known limitations

The mock is in-memory and single-process. It does not model a distributed database, message broker, ad auction, third-party measurement vendor, real-time clock skew, or production authentication. Node's event loop and synchronous state updates make the budget race deterministic in this implementation; a distributed production service would need transactional budget reservation or another atomic coordination mechanism.

The API uses an explicit accept/process split to make the in-flight boundary testable. The timestamps are generated by the server clock; production tests should inject a controllable clock and test clock skew and delayed event arrival.


## Fixture and test-data strategy

- `tests/fixtures/test.ts` owns automatic test isolation and reusable Playwright fixtures.
- `tests/fixtures/data.ts` owns named valid and invalid datasets.
- `tests/fixtures/types.ts` defines shared fixture contracts.
- `src/api-client.ts` centralizes endpoint paths and HTTP operations.
- Specs focus on behavior and assertions rather than repeated setup.
